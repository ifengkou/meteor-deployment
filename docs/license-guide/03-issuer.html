Issuer 签发流程

我方如何生成、签发与重试

issuer 只在我方运行。客户生成申请，我方签发文件；文件入网后，由目标服务 SDK 判断能否使用。
客户申请商业：IC1 或申请文件
恢复：RC1J/RC1A + 安装/服务
→
我方审核客户、机器、期限；或异常目标与窗口
→
issuer CLI调用同一个终端无关应用服务
→
签名输出文件 + SHA256；签发记录保留在我方

第一次准备：安装固定 SDK 与私钥

  1. Python 3.12；将 SHA256SUMS 对应的 SDK 0.6.0 wheel 放入 issuer/wheelhouse。
  2. 在 issuer 根目录按 uv.lock 安装依赖。离线执行前，先准备完整依赖缓存；单个 SDK wheel 不够。
  3. 创建我方私有记录/输出目录，再生成加密 Ed25519 私钥。生成已有文件时会拒绝覆盖。
命令示例；默认安全提示输入私钥口令
# 在 license-issuer 项目根目录执行；替换为已创建的我方目录
uv sync --locked
uv run --locked license-issuer keygen --key-id vendor-2026 \
  --private-key /absolute/vendor/private.pem \
  --public-key /absolute/vendor/public.pem

Python 示例，在已安装 cryptography 的我方环境执行；只转换公钥
# 我方构建环境：把 keygen 的 PEM 公钥转为两种构建输入
import base64, json
from pathlib import Path
from cryptography.hazmat.primitives import serialization

public = serialization.load_pem_public_key(
    Path("/absolute/vendor/public.pem").read_bytes()
)
der = public.public_bytes(serialization.Encoding.DER,
                          serialization.PublicFormat.SubjectPublicKeyInfo)
keys = {"vendor-2026": base64.b64encode(der).decode("ascii")}
Path("/absolute/vendor/ai-trusted-keys.json").write_text(json.dumps(keys))
Path("/absolute/vendor/metor-trust.json").write_text(json.dumps({
    "trust_version": "vendor-2026", "trusted_keys": keys
}))

两个产品固定同一个 key ID 和公钥，才能接受相应签名。这里只固定受控公钥，不能把任意客户上传的 key ID/公钥当作信任。

商业签发：四种组合怎么选？

选择CLI 参数客户提供
绑定、限时--binding HOST_INSTALL --validity TERM--request-file 或 --request-code；同时提供起止时间
绑定、无限期--binding HOST_INSTALL --validity PERPETUAL申请；只提供 not-before，省略 expires-at
无绑定、限时--binding UNBOUND --validity TERM不带申请/机器码；提供起止时间
无绑定、无限期--binding UNBOUND --validity PERPETUAL不带申请/机器码；只提供 not-before
商业命令示例；先设定时间变量和规范 UUID，再执行
# 以下变量由本次商业合同确定；每次新签发使用新的 UUID
# NOT_BEFORE_UTC / EXPIRES_AT_UTC 格式：YYYY-MM-DDTHH:mm:ssZ
uv run --locked --offline license-issuer sign-license --product icp-diag \
  --key-id vendor-2026 --private-key /absolute/vendor/private.pem \
  --customer-id customer-001 --customer-name '示例客户' \
  --binding HOST_INSTALL --request-file /absolute/vendor/license-request.json \
  --validity TERM --not-before "$NOT_BEFORE_UTC" --expires-at "$EXPIRES_AT_UTC" \
  --records-dir /absolute/vendor/records --output /absolute/vendor/license.json \
  --issuance-id "$COMMERCIAL_ISSUANCE_ID"

恢复签发：使用另一种用途

恢复命令示例；参数文件由我方本地生成，重试不能重新生成窗口/编号
# 先按恢复指南一次性生成并保留 recovery-params.env
. /absolute/vendor/recovery-params.env
uv run --locked --offline license-issuer sign-recovery --product icp-diag \
  --key-id vendor-2026 --private-key /absolute/vendor/private.pem \
  --request-file /absolute/vendor/recovery-request.json \
  --window-start "$RECOVERY_START_UTC" --window-end "$RECOVERY_END_UTC" \
  --records-dir /absolute/vendor/records --output /absolute/vendor/recovery.json \
  --issuance-id "$RECOVERY_ISSUANCE_ID"

内网禁止导出申请时，把 --request-file 替换为 --installation-id UUID --service metor --recovery-code RC1J-…，AI 则为 ai / RC1A。签发起点不能晚于窗口开始，首次应用不得达到窗口结束；窗口总约束见时间页。

同 ID 重试如何避免重复签发？

PREPARED先记录编号、参数指纹与签发时间
→
签名与暂存固定完整字节及 SHA256
→
原子输出已有不同文件不覆盖
→
ISSUED确认完成；重试返回原字节
失败或结果未知时：保留原编号、原参数、原记录目录和输出现场。换新编号重试会变成一次新的签发。商业与恢复不能复用同一编号；同编号重试也不能偷偷换窗口或期限。

恢复与商业签发均可复用 IssuerApplication，未来 Web 后端可直接调用 sign_license / sign_recovery；当前没有 issuer Web 页面。verify 子命令只验证商业许可，恢复文件由目标服务 SDK 验证。
