防时间回拨与恢复

时间为何只前进，何时允许重建

防回拨：普通运行不降低时间基准。恢复：客户先校正系统 UTC，再由我方签名批准本服务重建一次 SDK 时间基准。恢复不修改操作系统时间。

三个时间来源

W：系统 UTC可能被运维或用户调整
→
R：保护参考持久高水位、单调时钟推算、内存高水位取最大
→
T：有效校验时间max(W, R)，商业期限按它判断
伪代码，不直接执行
R = max(clock.high_watermark,
        启动锚点 + 单调时钟经过时间,
        本进程已观察的有效时间)
T = max(W, R)
if W + 86400秒 < R:
  CLOCK_ROLLBACK → 受控入口拒绝
else:
  用 T 校验商业许可的精确期限

生命周期每 30 秒 checkpoint；请求 require_valid 只观察，不强制落盘。
例子结果原因
已记住 10/23，把系统改为 2/1CLOCK_ROLLBACK，受控操作 403落后超过一天；不会得到额外使用月份
仅调早 12 小时不因回拨本身拒绝，但有效时间不下降一天容差不是商业期限宽限
误调到 10/30，记录后校回 10/23可能仍拒绝，需要签名恢复旧高水位不能自行降回 10/23
服务重启继续读取持久高水位重启不等于重置时钟
删除/改坏 clockCLOCK_STATE_INVALID不会自动补造时间种子

恢复申请绑定的是哪一次异常？

当前异常读取本服务 clock 的原始字节摘要
→
持久挑战安装 UUID + service + nonce + 状态摘要
→
target_id / RC1同一适用挑战重复取得不换码
→
我方恢复签名绑定目标、恢复 ID 和窗口

恢复挑战写入本服务的 recovery-challenge.json 并用安装密钥按用途派生 HMAC。原目标发生变化后，旧恢复文件通常不能用于新的异常。安装身份或主密钥损坏不能靠普通时间恢复修复。

应用恢复的顺序

伪代码，不直接执行
applyRecovery(文件)
  保留原管理员 / ControlProof 鉴权
  验签、产品、安装 UUID、service 校验
  获取同一 Runtime 锁和本服务状态文件锁
  if 当前有效 clock.last_recovery_id == 文件.recovery_id:
    确认持久性 → ALREADY_APPLIED，不再降低高水位
  else:
    校验 window_start <= 系统 UTC < window_end
    校验异常仍适用、挑战 HMAC、当前状态摘要、target_id
    写新 clock：已确认 epoch 基数 + 1（无基数时从 1 开始）
              sequence=0，高水位=当前 UTC
    原子替换并确认文件/目录持久性
    未确认：OUTCOME_UNKNOWN，保持受限，同文件重试
    已确认：刷新同一 Runtime 的内存锚点，返回 APPLIED
  再观察原商业许可：过期仍 EXPIRED

恢复窗口只限制首次应用

字段含义
RECOVERY_START_UTC最早可首次应用的 UTC，包含该时刻
RECOVERY_END_UTC首次应用失效时刻，不包含该时刻
签发约束issued_at ≤ start < end ≤ issued_at + 7 天
同 ID 再确认当前 clock 已记录该恢复 ID 时，可在窗口后确认；不再次重置
与商业期限的关系恢复不延长 expires_at；一天回拨容差也不扩展恢复窗口

交互理解：这只是模型演示

假设商业许可于 2026-11-01 00:00 UTC 到期。先选择场景，再尝试恢复。

固定演示窗口：2026-10-23 00:00 ≤ W < 2026-10-25 00:00 UTC。模型不执行 SDK、不写文件、不调整真实时钟；省略实际签名、HMAC、并发和存储细节。
离线边界：SDK 没有可信在线时间源，不能自行知道“真实日期”。该方案依赖运维校时及我方审核批准恢复；不承诺抵御整机历史快照回滚或客户管理员主动改程序/本地密钥。
