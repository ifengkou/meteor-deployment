AI Runtime 集成与运行

Python 装配、独立校验与 ControlProof

AI 自己验证本地 License。浏览器调用可经过 Metor 的原网关鉴权，但 Metor 的许可结果不会作为 AI 的放行依据。

我方构建接入步骤

  1. 将 metor_license_core-0.6.0 wheel 放入 AI 自己的 wheelhouse，uv.lock 固定实际文件及摘要。
  2. 准备目标 Linux/Python 3.12 的全部第三方依赖；准备基础镜像、模型等已有部署输入。
  3. 将仅含 key ID → Base64 DER SPKI 的公钥映射放到 license-build/trusted-keys.json。
  4. 维护 app/license-routes.json；客户构建固定 CUSTOMER_REQUIRED、公钥、trust_version 和清单原始字节摘要。
  5. 运行环境预装 SDK 与全部依赖，使用本服务独立 state/ai 挂载；客户启动不执行 pip/uv。
我方构建期操作；Dockerfile 已执行同一元数据步骤，通常不需手工修改运行目录
# 我方制作完整 wheelhouse；架构必须匹配客户目标
TARGET_PLATFORM=linux/arm64 deployment/scripts/prepare-wheelhouse.sh
# 若目标为 AMD64，改为 linux/amd64，不混用 ARM64 wheel

# 在 ai-runtime-service 根目录：客户元数据构建命令形状
.venv/bin/python tools/build_license_metadata.py \
  --trust-bundle /absolute/vendor/ai-trusted-keys.json \

正常请求与恢复请求是两条路径

业务请求

AI 本地中间件根据清单判断；固定 invoke 首行也检查。未命中且非固定入口保持原逻辑。

维护请求

健康/诊断/恢复是精确例外；恢复仍验证安装级 ControlProof，不因时钟记录损坏而丢失全部维护入口。

AI 恢复不需要 Metor 在线

宿主 local-stack.py只使用标准库和 Docker
→
AI 容器内维护客户端读安装凭据，生成短期 ControlProof
→
AI 在线恢复 API验证 scope / method / path / body
→
运行中的同一 Runtime取得申请或原子应用恢复

客户端为了生成证明可以读取安装身份与密钥；它不写 clock。真正的状态修改、锁和内存刷新都发生在 AI 服务进程的既有 Runtime 中。Proof 不是用户 JWT，也不是商业签名；签发恢复文件仍需要我方 issuer。

AI 运维命令；模块已在镜像内，宿主不需要安装 SDK
# 在工作区 / 交付包根目录，替换私有配置与文件路径
python3 deployment/scripts/local-stack.py --env-file /absolute/docker.env \
  license-recovery request --output /absolute/ai-recovery-request.json

python3 deployment/scripts/local-stack.py --env-file /absolute/docker.env \
  license-recovery apply --file /absolute/recovery.json
API认证与输入
POST /internal/license/recovery/requestLICENSE_RECOVERY_REQUEST；无参数/请求体
POST /internal/license/recovery/applyLICENSE_RECOVERY_APPLY；原始恢复文件字节，最多 64KiB
GET /internal/license/status本服务内部诊断，沿用其已有认证约定
POST /internal/license/validate商业候选预检，不发布、不清除时间异常

两个恢复 scope 的证明绑定安装、HTTP 方法、精确路径、原始 body SHA256、随机编号和短期时间；最长 60 秒，传输校差 5 秒。它和商业期限、恢复文件窗口的含义不同。
