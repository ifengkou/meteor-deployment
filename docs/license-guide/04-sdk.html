Runtime 生命周期：不要每请求重新创建

伪代码，不直接执行
application.start
  load 固定发行模式 / 固定公钥
  verify 包内清单摘要 → 不可变策略
  create 一个 Runtime（本服务 identity / clock / service）
  create 一个产品 guard（策略状态 + Runtime）
  inject guard 到 HTTP 层及固定关键方法
  start 每 30 秒 checkpoint 的生命周期任务

  账号权限照常检查
  命中受控入口 → 这个 guard.requireValid()

  同一个 Runtime.applyRecovery(原始文件字节)

  停止生命周期任务，保留持久状态

底层 CommercialLicenseVerifier / verify_license 只使用调用方提供的时间与身份。只引入这个底层 API，不会自动获得持久防回拨。需要防回拨和恢复时，产品必须使用长生命周期 Runtime。

接入顺序与约束

  1. 安装器生成安装 UUID、32 字节 service.key 与各服务时间种子；Runtime 不自动补造。
  2. 构造实际 ProductProfile / Java Config，固定产品域和 service；Java Config 显式配置 RC1J。
  3. 产品 guard 必填，禁止 None、缺省放行和每请求新建 Runtime。
  4. 请求只观察；定时 checkpoint 即使没有请求也运行。异步 Python 将文件操作放到工作线程。
  5. 恢复成功后同一实例刷新锚点；不能让控制器旁路写 clock，再期待旧内存自动切换。
  6. 一个服务进程使用自己的 state 目录；不提供多副本共享 clock 的内存协调。
