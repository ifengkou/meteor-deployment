授权控制机制

谁签发、谁校验、控制什么

一句话：我方用私钥签发，客户服务用固定公钥 + 本机身份 + 受保护时间独立校验。
我方 issuer私钥与签发记录留在我方
→
签名许可文件文件入网，支持线下传递
→
客户本地 SDK不向我方或另一服务查询许可
→
当前请求通过继续，失败返回授权响应

一张文件，两项独立选择

维度选项实际含义
机器HOST_INSTALL绑定宿主 machine-id 和安装 UUID 派生的 binding_id
机器UNBOUND不比较机器绑定，但仍需要安装身份与时间记录
期限TERM包含 not_before；达到 expires_at 即到期
期限PERPETUAL没有到期时间，仍校验签名、产品和 not_before

四种组合都可由我方明确签发。无限期、无绑定和开发模式是三件不同的事。 客户发行不能用运行参数切到开发模式。

许可文件为什么不能直接改日期？

原始 JSON 载荷包含产品、绑定、期限、key_id 等
→
Ed25519 签名签发私钥签原始载荷字节
→
SDK 固定公钥验签改任一载荷字节，原签名就不能通过
伪代码，不直接执行
envelope = { payload: Base64URL(原始载荷字节), signature: Base64URL(签名) }
verify(原始载荷, 固定信任中的公钥)
check product_id
if HOST_INSTALL: compare 本机重新计算的 binding_id
check protected_time >= not_before
if TERM: check protected_time < expires_at

同一个 License，服务各自判断

Metor

可读取 shared/active.license.json；使用自己的 state/metor/clock.json。

AI Runtime

可读取同一商业文件；使用自己的 state/ai/clock.json，不信任 Metor 已校验的声明。

默认 Compose 共用一个安装身份与商业文件。Metor 导入成功说明本地发布完成，不表示 AI 已确认；两个服务各自观察文件变化。若分开部署且不共享目录，需要分别提供文件。

实际运行的检查边界

伪代码，不直接执行
request
  原身份权限检查（产品已有）
  启动策略无效？
    精确维护入口：保留原鉴权
    其他业务：拒绝 LICENSE_POLICY_INVALID
  策略有效且匹配受控 API？
    是：guard.requireValid / require_valid
    否：继续原链路
  少数固定关键方法入口
    再调用同一 guard，覆盖直接调用
  原业务处理

Metor 的固定关键方法为 TicketService.create；AI 为 InvocationService.invoke。SDK 不介入排队、租约、重试或业务实体，也不通过许可状态把所有菜单变成只读。
